# ACS email delivery shadow ingestion

This endpoint records authenticated Azure Communication Services email delivery reports in a durable, organization-independent inbox. Shadow ingestion does not update password-reset validity, delivery state, or tenant audit events.

This reviewed source change is not a deployment or activation record. It does not authorize database grants, migration execution, environment changes, Event Grid subscription creation, ingestion enablement, projection enablement, traffic activation, or production canaries. Keep `ACS_EVENT_GRID_INGESTION_ENABLED=false` and `ACS_EMAIL_DELIVERY_PROJECTION_ENABLED=false` unless a separately approved operational change has satisfied every applicable gate below.

## Dark deployment gate

1. Verify that ingestion is disabled, drain any older web revision that could have enabled it, and confirm there are no active receipt writers. Then apply the reviewed inbox migrations to every application and worker environment through the dedicated migration owner. The `ACCESS EXCLUSIVE` migration lock protects the catalog change; it is not a substitute for quiescing ingress traffic.
2. Run migrations through the dedicated role that owns `provider_event_inbox`, is neither `vaultspace_app` nor the ingress login, and whose exact lowercase PostgreSQL role name is configured in `EVENT_GRID_INBOX_EXPECTED_OWNER`. Do not casually change ownership to make a preflight pass; owner drift is a security-posture incident until the catalog and the deployed migration identity are reconciled. Create an isolated, non-inheriting, non-superuser ingress database login used only by `EVENT_GRID_INGRESS_DATABASE_URL`. Its required eventual table-grant shape is `USAGE` on schema `public` plus non-grantable `SELECT`, `INSERT`, and `UPDATE` only on `provider_event_inbox`, with no column-level grants. It must have no inherited role memberships, database or schema `CREATE`, sequence privileges, protected-function execution, or privileges on any other application table or column. The ordinary `vaultspace_app` role must have no inbox privileges, must not own the inbox, and must have no direct or indirect role memberships that can be reached through `SET ROLE`. The migration does not grant those deployment-specific table privileges; operators must establish and verify them separately. Run the fail-closed RLS repair verification for `vaultspace_app` after any role or grant change.
3. Deploy the endpoint with `ACS_EVENT_GRID_INGESTION_ENABLED=false` and drain older application revisions.
4. Configure a single-tenant Entra application to accept v2 access tokens, add the `idtyp` optional access-token claim, and expose the `AzureEventGridSecureWebhookSubscriber` application role. Use the application client-ID GUID as the expected v2 audience. Pin the Microsoft.EventGrid application ID for the deployed Azure cloud. In a controlled canary, verify the literal `iss`, `aud`, `azp`, `idtyp=app`, `roles`, `tid`, and optional `oid` contract without recording the bearer token.
5. Configure a dedicated, versioned payload-fingerprint key ring. Retain retired keys through the maximum Event Grid retry and replay horizon.
6. Configure an encrypted Blob dead-letter container with managed-identity RBAC, access auditing, short retention, capacity/failure alerts, and explicit incident ownership. This is a privacy exception because dead letters contain the original ACS event, including email addresses.
7. Disable authorization-header and request-body capture in the ingress proxy, WAF, platform request logging, Application Insights, and exception middleware. Verify from the deployed environment that every capture path is disabled before changing `ACS_EVENT_GRID_INGESTION_ENABLED` or creating an Event Grid subscription.
8. Only after steps 1 through 7 pass and a separate operational approval exists, temporarily enable shadow ingestion and create the Event Grid subscription with Microsoft Entra webhook authentication, an exact `Microsoft.Communication.EmailDeliveryReportReceived` filter, and `maxEventsPerBatch=1`. The endpoint deliberately accepts exactly one notification event, so subscription validation cannot succeed while ingestion is disabled.
9. Validate the authenticated subscription handshake, one real delivery receipt, exact duplicate delivery, a temporary 503 retry, conflict quarantine, and dead-letter creation/alerting. Return the feature flag to false if any canary fails.
10. Keep `ACS_EMAIL_DELIVERY_PROJECTION_ENABLED=false` until the separately reviewed protected projector, operational grants, cutover configuration, real ACS message-ID correlation canary, and live rollout are approved.
11. Keep production ingestion disabled until a separately reviewed dead-letter recovery mechanism exists. Chunk 4B treats dead letters as access-controlled forensic evidence and does not provide replay.

## Response contract

- `200`: validation handshake, committed new receipt, exact duplicate, quarantined authenticated evidence, or durably recorded conflict.
- `400`: permanently invalid Event Grid schema, event type, source pair, or timestamp alias conflict.
- `401` or `403`: invalid token or unauthorized caller.
- `413` or `415`: over-limit or unsupported request framing.
- `503`: JWKS, configuration-key, or database failure. Event Grid should retry these responses. A recognized database-guard rejection still receives the same generic response, but it is a potential persistent ownership-contract or writer-drift incident, not ordinary database unavailability.

The endpoint authenticates before reading the body, streams through a hard byte limit, and commits the complete bounded batch before returning `200`. It never logs or stores the bearer token, raw body, sender, recipient, subject, or validation URL. The protected inbox stores the bounded provider message identifier, an allowlisted categorical provider status when recognized, and pseudonymous fingerprints needed for later correlation and conflict detection. Those protected values must not be copied into ordinary logs, tickets, chat, or shell history.

## Provider inbox ownership boundary and preflight

The state-ownership migration `20260731080000_separate_provider_inbox_state_ownership` establishes a database boundary when it is applied and verified. It does not create a runtime projector identity, protected projector function, inbox consumer, scheduler, correlation lookup, tenant audit writer, or projection activation.

The dedicated migration owner owns the inbox and the guard function. It is the only identity the trigger recognizes for ordinary processing-domain writes, but it is not a runtime credential and must not be distributed to the route, worker, or ordinary application runtime. Even ordinary owner writes cannot rewrite first-seen evidence, reverse a terminal conflict, or rewrite first-conflict evidence. PostgreSQL ownership remains a privileged trust root: an owner can perform destructive DDL, disable or replace triggers, and exercise owner-level `DELETE` or `TRUNCATE` authority. The trigger is not a security boundary against compromise or misuse of the owner credential. Restrict and monitor owner credentials for approved migrations only, never use them for data remediation or runtime projection, and require separate incident or migration approval for evidence deletion, truncation, trigger disabling, or ownership changes.

The isolated ingress login retains table-level `SELECT`, `INSERT`, and `UPDATE` because receipt correlation and atomic conflict observation require them. Those grants are not general update authority. The trigger permits ingress to insert only internally consistent, database-timestamped `PENDING` or `QUARANTINED` receipts. It permits an update only for one atomic, monotonic conflict observation: the count increases by one, the row becomes `CONFLICT`, the categorical conflict error is set, the observed conflicting fingerprint is a non-original 64-character lowercase hexadecimal value, and a processing lease is cleared. The update preserves first-seen and quarantine evidence, processing attempts, schedule, and `processedAt`. Once `CONFLICT`, the row cannot return to a non-conflict state; an exact no-op is not a general ingress update capability. Ingress cannot mutate evidence, attempts, schedules, ordinary errors, leases, or processed state except for the database-enforced lease clearing that is part of an accepted conflict observation. It does not need or receive `EXECUTE` on the trigger function for the trigger to run.

`vaultspace_app` has no direct or inherited inbox access. A later protected projector path may own processing behavior, but no such path exists or is enabled by this change.

Run `npm run worker:provider-event-preflight` only with the dedicated ingress database URL, the exact expected migration-owner name, and the matched release configuration. Do not substitute `DATABASE_URL_ADMIN`, run it as the owner, grant more privileges, disable the trigger, bypass the expected-owner check, or grant direct trigger-function execution to make it pass. The preflight validates the effective role boundary, owner, table and column ACLs, trigger attachment, guard-function posture and reviewed SHA-256 source binding. It proves normalized `PENDING` and `QUARANTINED` inserts, constrained conflict behavior, evidence preservation, and denial of projector-owned mutations with exact SQLSTATE and guard-rule checks. All canaries run in one forced-rollback transaction with a five-second acquisition bound and a thirty-second transaction bound. A success requires all canaries and the rollback sentinel, and leaves no canary receipt or privilege change behind. It does not validate Entra configuration, Event Grid delivery, proxy logging, dead-lettering, live ACS correlation, tenant audit projection, or overall production health.

## State-ownership migration recovery

The state-ownership migration is one Prisma-visible PostgreSQL `DO` statement. Its migration connection must establish `lock_timeout = 10s` and `statement_timeout = 120s` before Prisma submits that statement. Run it only through `MIGRATION_DATABASE_URL=<dedicated migration-owner URL> npm run db:migrate`. The wrapper's variable name does not prove identity: a runtime or ingress URL is forbidden even if the wrapper accepts its syntax, and the migration's owner/posture proof must reject it. The Docker entrypoint's `DATABASE_URL` fallback is local single-role compatibility only, not an approved production path for this migration. The migration also sets the same transaction-local values before requesting its `ACCESS EXCLUSIVE` lock on `provider_event_inbox`; that in-statement setting enforces the lock-acquisition bound but cannot retroactively establish a full-statement deadline. Do not claim the 120-second deadline is verified until the exact migration connection path has demonstrated it. Before changing the guard, the migration rejects preexisting rows outside the narrow reviewed predecessor shapes, including malformed timestamp evidence and any already-persisted projector state. `PROVIDER_EVENT_INBOX_PREEXISTING_STATE_INVALID` is an evidence incident. Keep ingestion and projection disabled, preserve the database and protected logs, investigate with approved read-only queries and categorical counts first, and require separately reviewed remediation for anomalous source data. Never delete, normalize, reset, force-update, or rewrite provider evidence merely to make the migration pass. Do not edit the deployed migration or weaken its predecessor proof.

The one-statement shape is deliberate. With Prisma 5.22, an explicit `BEGIN` or trailing migration statement can replace the actionable precondition failure with `25P02` (`current transaction is aborted`). A dirty-predecessor deployment must instead expose PostgreSQL `P0001` and the exact primary message `PROVIDER_EVENT_INBOX_PREEXISTING_STATE_INVALID`. Treat missing, masked, or differently categorized primary diagnostics as a release blocker, not as a reason to weaken the check or accept `25P02`.

A confirmed lock timeout, statement timeout, or precondition failure rolls back the migration transaction's validation, guard-function replacement, trigger replacement, and function-ACL changes together. Because this migration replaces existing objects with the same names, do not infer rollback from object absence alone. Reconcile exactly one of these states before any retry:

1. The fully committed successor posture, with Prisma recording the migration as finished and direct catalog inspection proving the exact successor guard function, source, owner, trigger, constraints, and ACL effects attributable to this migration.
2. The confirmed rolled-back predecessor posture, with no successful Prisma record, no active migration transaction, and direct catalog inspection proving the predecessor posture.
3. An ambiguous or mixed posture, where Prisma and catalog evidence disagree, the transaction remains active, or neither exact posture can be established. Treat this as an incident. Do not rerun, resolve, or repair it ad hoc.

For a confirmed rollback recorded as failed by Prisma, `prisma migrate resolve --rolled-back 20260731080000_separate_provider_inbox_state_ownership` is appropriate only after the rollback has been independently verified. Do not use `--applied` merely to clear an error. Only after separately approved ingress-role creation and grants should the ingress preflight be required as an operational-readiness gate. Operators may inspect `pg_stat_activity`, `pg_locks`, `pg_blocking_pids`, transaction age, backend identity, and wait class, but should not copy full SQL text or protected receipt values into incident systems. Do not terminate an unrelated session without separate approval, increase timeouts as the first response, disable the trigger or constraints, grant broad privileges, run manual evidence updates, or retry continuously while the blocker remains. Drain or stop the identified approved writer, allow its transaction to finish, and rerun the unchanged migration only after the blocker is safely resolved.

## Safe diagnostics and guard incidents

The preflight CLI emits only reviewed categorical diagnostics: component, event, outcome, contract version, bounded allowlisted release label, deployment mode, observation time, effective-role category, and a stable error code. `APP_RELEASE` must contain only a non-sensitive release identifier; its grammar and length bound do not make an operator-supplied secret safe. The preflight does not intentionally emit a database URL, role name, SQL, raw Prisma error, provider message identifier, event fingerprint, payload fingerprint, or canary receipt ID. The dedicated ingress Prisma client has automatic raw error and warning logging disabled so caller-provided categorical diagnostics are the reviewed diagnostic surface. This does not make proxy, WAF, platform request capture, Application Insights, or exception middleware safe automatically; those remain separate operational controls.

The Event Grid route returns only generic `503 Service unavailable` for all database failures. When a Prisma `P2010` error has PostgreSQL `P0001` and an exact allowlisted primary guard rule, the server logs `component`, `event`, `outcome`, `requestId`, `status`, `EVENT_GRID_DATABASE_GUARD_REJECTED`, and a safe `databaseGuardRule`; the rule is never returned to Event Grid. The recognized rules are `PROVIDER_EVENT_INGRESS_INITIAL_STATE_INVALID`, `PROVIDER_EVENT_FIRST_SEEN_EVIDENCE_IMMUTABLE`, `PROVIDER_EVENT_CONFLICT_TERMINAL`, `PROVIDER_EVENT_CONFLICT_MONOTONICITY_INVALID`, `PROVIDER_EVENT_FIRST_CONFLICT_IMMUTABLE`, and `PROVIDER_EVENT_CONFLICT_INTENT_INVALID`. Unknown, malformed, context-only, or differently coded database errors remain `EVENT_GRID_INGESTION_UNAVAILABLE` and include no guard rule. Repeated recognized guard failures indicate possible deployment, schema, trigger, privilege, or writer drift. In any future separately approved rollout, stop or disable ingress through the approved gate, preserve only the route's safe request ID, status, categorical error code, and optional rule, then investigate the reviewed posture after traffic is quiesced. If separately approved platform or deployment metadata supplies a timestamp or release label, treat it as distinct metadata rather than a route-emitted field. Do not weaken caller authentication or replay a dead-letter blob into this webhook; generate a fresh controlled canary only after correction and separate activation approval.

## Dead-letter recovery boundary

Azure Communication Services system-topic events cannot be operator-published, and an operator token cannot satisfy the endpoint's pinned Microsoft.EventGrid caller identity. Therefore, operators must not submit dead-letter blobs to this webhook or weaken its caller pin. Chunk 4B has no replay claim. Until a separate recovery path with equivalent validation, PII controls, durable operator audit, and independent security review is implemented, preserve the encrypted object only for the approved retention window, use approved protected diagnostic tooling for any fingerprint analysis, use only categorical counts and error codes in ordinary incident systems, and generate a fresh canary event after correction. Never paste dead-letter payloads, raw or pseudonymous fingerprints, or provider identifiers into tickets, chat, logs, or command history.
